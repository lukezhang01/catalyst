# Lessons Learned: Done vs. Usable

Quantifying user friction through the Critical User Journey (CUJ) framework fundamentally shifted our engineering perspective from evaluating software by whether it compiles to evaluating whether it provides effortless utility under real-world pressure. In software engineering coursework, the definition of "done" is often defined by technical compliance: clean backend routing, error-free builds, passing tests, and modular architecture. However, conducting a rigorous CUJ audit forced us to confront the stark reality that a technically "done" application can still be virtually unusable for its target end user.

During our initial development sprint, our focus was almost exclusively on structural correctness. We built a decoupled system separating a FastAPI Python backend (`main.py`, `store.py`) from a modern React/Vite frontend. We engineered custom hooks (`useDualTimer.js`) to manage presentation and Q&A timing states, integrated audio notifications (`chime.js`), and established persistent state using local JSON files (`session.json`). To our team, the MVP was complete the moment the frontend successfully communicated with backend endpoints to select and render a random team on screen.

However, auditing the Unhappy Path through the eyes of our persona—Prof. John Doe, an instructor from outside the CS department—shattered this assumption. Because Prof. Doe operates outside a standard software development environment, his machine lacked pre-installed developer tools like Python 3, virtual environment modules (`venv`), Node.js, and package managers like `npm` or `vite`. Before he could even launch our application, he spent over 20 minutes searching online documentation, resolving CLI path errors, and manually configuring a local execution environment. From a developer standpoint, local CLI startup scripts are standard practice; from a non-technical user’s perspective, they represent an immediate, high-friction barrier to entry.

Once inside the app, the friction continued. To prepare for a lecture session with 40+ students, Prof. Doe was forced to use `AddTeamForm.jsx` to manually type team names, project titles, and individual member names one by one. Tracking task completion time revealed that this administrative data entry consumed over 15 minutes of class time before a single presentation could even begin. Furthermore, attempting to add late-arriving students mid-session created severe context switches, forcing the instructor to split mental focus between evaluating live student presentations and navigating form fields.

Quantifying these context switches, setup delays, and task durations redefined our concept of completion. We realized that true usability is not about adding more internal features; it is about protecting the user's focus and reducing cognitive load. Features that seemed minor during development—such as cloud hosting to bypass local environment setups, or bulk CSV/JSON roster imports—are actually critical to making the tool usable in a live classroom environment. Moving forward into Assignment 3, this exercise has fundamentally re-anchored our product roadmap around user ergonomics over pure technical capability.
